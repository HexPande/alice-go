# Правила работы и публикации

## Проект

- Приложение на Go и PocketBase; YAML-конфигурация читается через Viper.
- Единственный установщик — корневой `install.sh`. Он должен работать через `sh -c "$(curl -fsSL ...)"`, без Python, GitHub CLI и повторного скачивания другого скрипта.
- README — публичная страница: назначение, системные требования, установка, обновление и подключение к Алисе. Внутренние инструкции размещайте здесь. Не создавайте каталог `docs` без запроса.
- Проверка ОС, архитектуры и обязательных команд должна предшествовать изменениям установленного сервиса.
- При обновлении сохраняйте YAML-конфиг и создавайте резервную копию данных перед заменой бинарника.

## Когда публиковать

- Коммит, push и релиз выполняются по запросу пользователя.
- «Отправить в git» означает коммит и push; само по себе это не запрос на новый релиз.
- Push в `main` запускает проверки и сборку артефактов, но **не создаёт GitHub Release**.
- Установщик скачивает бинарники из последнего стабильного GitHub Release. Чтобы доставить изменения приложения пользователю, требуется новый релиз.
- Установщик скачивается из `main`: сохраняйте его совместимость с опубликованным релизом при изменении интерфейса CLI или формата конфигурации.

## 1. Проверки перед публикацией

Работайте из корня репозитория. Используйте Go 1.27.1 (версия закреплена в `.github/workflows/ci.yml`).

```sh
git status --short --branch
git diff
git diff --cached
git log --oneline -10
go mod tidy
go test -race -shuffle=on ./...
go vet ./...
go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.14.0 run ./...
go run golang.org/x/vuln/cmd/govulncheck@v1.8.0 ./...
sh -n install.sh
shellcheck install.sh scripts/package.sh scripts/install_test.sh
bash scripts/install_test.sh
make package
git diff --check
```

Тесты установщика дополнительно извлекают и проверяют встроенный Bash-код. Локальный ShellCheck может отличаться от версии на runner: окончательная проверка — успешный CI в GitHub.

Не включайте в коммит `dist/`, `bin/`, `pb_data/`, локальные конфиги и секреты. Проверяйте staged diff и добавляйте только относящиеся к задаче файлы. Сообщения коммитов — Conventional Commits.

## 2. Коммит, push и CI

После коммита:

```sh
git push origin main
gh run list --repo HexPande/alice-go --branch main --limit 5 \
  --json databaseId,headSha,status,conclusion,url
```

Найдите запуск для **отправленного SHA**, а не просто последний запуск:

```sh
gh run watch <RUN_ID> --repo HexPande/alice-go --exit-status
```

При ошибке:

```sh
gh run view <RUN_ID> --repo HexPande/alice-go --log-failed
```

Исправьте причину, создайте новый коммит и дождитесь успешного CI. Не отключайте проверки ради публикации. GitHub CLI должен быть авторизован через `gh auth login`.

## 3. Создание релиза

Убедитесь, что рабочее дерево чистое, нужный коммит находится в `origin/main`, а его CI завершился успешно. Проверьте существующие версии:

```sh
gh release list --repo HexPande/alice-go
git ls-remote --tags origin
```

Для новой версии создайте аннотированный тег (ниже пример первого релиза):

```sh
git tag -a v0.1.0 -m "Release v0.1.0"
git push origin v0.1.0
```

Workflow `CI and Release` сам выполнит проверки, соберёт файлы и создаст Release. Не создавайте его вручную параллельно workflow. Тег с дефисом, например `v0.2.0-rc.1`, публикуется как prerelease и не выбирается установщиком по умолчанию.

Дождитесь успешного запуска **для тега**. При исправлении уже опубликованной версии используйте новый тег; не передвигайте существующие теги и не заменяйте файлы опубликованного релиза.

## 4. Проверка публикации

```sh
gh release view v0.1.0 --repo HexPande/alice-go \
  --json tagName,isDraft,isPrerelease,url,assets
```

Стабильный релиз должен быть опубликован (не draft и не prerelease) и содержать:

- `alice-go_linux-arm64.tar.gz`
- `alice-go_linux-armv7.tar.gz`
- `SHA256SUMS`

Скачайте файлы в отдельный временный каталог через `gh release download`, проверьте контрольные суммы (`sha256sum -c SHA256SUMS` на Linux или `shasum -a 256 -c SHA256SUMS` на macOS) и состав архивов. В каждом архиве должны быть `alice`, `README.md` и `install.sh`.

Для стабильной версии проверьте, что `https://github.com/HexPande/alice-go/releases/latest` перенаправляет на нужный тег. Не запускайте установку на рабочем сервере без запроса пользователя.

Публикация завершена только после успешного workflow и проверки доступности файлов. В ответе укажите коммит, версию, ссылку на релиз и результат CI. Если публикация не удалась, явно укажите блокирующую причину.
